## Findings

### F-001 — Medium (architecture/security) — ADR index оставляет superseded write-contract ADR-006 безусловно активным

**Location:** `docs/adr/README.md:30-32`;
`docs/adr/ADR-008-headless-agent-write-boundary.md:54-56`.

ADR-008 явно отменяет automatic write по одному лишь consent ADR-006, однако
строка ADR-006 в canonical index по-прежнему имеет только статус `Accepted`.
Указание `supersedes` находится лишь в строке нового ADR. Это не выполняет
ручную consistency-проверку STEP-017 о том, что ADR-004/006/007/008 не
оставляют противоречивых активных boundary contracts.

**Scenario:** автор `STEP FIX STEP-009` открывает ADR-006 из index, видит
безусловно активный `Accepted` contract и сохраняет существующий automatic
spawn после workspace-wide confirmation, не дойдя до более поздней строки
ADR-008.

**Impact:** corrective implementation может сохранить именно security gap
F-002 STEP-009, для устранения которого создан STEP-017.

**Fix direction:** не меняя исторический текст ADR-006, пометить его строку в
ADR index как частично superseded ADR-008 в части automatic write flow; статус
ADR-008 оставить `Accepted`.

### F-002 — Medium (architecture/handoff) — Handoff F-003 двусмысленно требует automatic mode, который этим же ADR запрещён

**Location:** `docs/adr/ADR-008-headless-agent-write-boundary.md:31-48,87-98`;
`planning/tasks/STEP-017.md:109-122`.

Decision запрещает automatic write для всех текущих executor/platform
combinations и разрешает его только после отдельного ADR с новым evidence.
Однако обязательный handoff формулирует F-003 как «automatic mode получает
проверяемое containment detached descendants», тогда как для F-006 явно
предусмотрена альтернатива «automatic mode остаётся blocked». Не определено,
закрывает ли pre-spawn manual fallback F-003 сейчас или `STEP FIX STEP-009`
обязан вопреки Decision реализовать новый supervisor.

**Scenario:** FIX либо расширяет scope до cgroup/Job Object и возвращает
automatic write без требуемого отдельного ADR, либо оставляет F-003 формально
незакрытым даже после корректного manual fallback.

**Impact:** handoff F-001..F-007 не является однозначным, а следующий
corrective проход может нарушить принятую fail-closed boundary.

**Fix direction:** явно зафиксировать для F-003 тот же выбор: текущий FIX
закрывает finding отсутствием spawn в write-mode; containment и его regression
обязательны только при будущем отдельном решении вернуть automatic write.

### F-003 — Medium (traceability) — Architecture/status projections частично описывают состояние до ADR-008 и последнего FAIL review

**Location:** `docs/architecture.md:7,24-26`;
`planning/STATUS.md:7,11-12`.

Architecture по-прежнему описывает единый основной поток с automatic
делегированием, result/reload для mutating-команд, не показывая выбранную
ветку manual handoff без child process и без automatic result/reload.
Одновременно Summary STATUS не включает STEP-017 в состав roadmap и говорит,
что STEP-009 «ждёт независимого review», хотя review `16:14Z` уже дал `FAIL` и
ниже тот же файл правильно направляет работу в `STEP FIX STEP-009`.

**Scenario:** читатель architecture/status ожидает, что mutating command после
STEP-017 всё ещё автоматически запускает executor и что STEP-009 ещё не
reviewed, тогда как canonical decision требует pre-spawn manual fallback после
уже состоявшегося FAIL review.

**Impact:** acceptance criterion о синхронизированных architecture baseline и
planning projections не выполнен; project status даёт две разные картины
текущего состояния.

**Fix direction:** добавить в основной flow явную mutating/manual ветку ADR-008
и синхронизировать Summary STATUS с STEP-017 и фактическим FAIL STEP-009.
