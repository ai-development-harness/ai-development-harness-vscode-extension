### F-001 [Blocking] — точечная инвалидация дерева не доходит до UI: refresh по file watcher и после мутаций фактически не работает

**Location:** `src/explorer/treeProvider.ts:44-52` (`invalidate`) и `:58-61` (`getChildren(undefined)`); потребители — `src/explorer/refresh.ts:70`, `src/explorer/actions.ts:202`, `:224`, `:260`.

`getChildren(undefined)` возвращает **заново аллоцированные** объекты на каждый вызов:

```ts
return GROUP_IDS.map((id) => ({ kind: 'group', id }) as const);
```

а `invalidate(groupId)` фаерит **ещё один новый литерал**:

```ts
this._onDidChangeTreeData.fire({ kind: 'group', id: groupId });
```

В фактически используемой сборке VSCode 1.138.0 (`.vscode-test/vscode-linux-x64-1.138.0/.../extensionHostProcess.js`) обработка выглядит так:

```js
_refresh(e){ if(e.some(o=>!o)) { ... return this._proxy.$refresh(this._viewId); }
             { let o=this._getHandlesToRefresh(e); if(o.length) return this._refreshHandles(o) }
             return Promise.resolve(void 0) }
_getHandlesToRefresh(e){ let n=new Set, o=e.map(s=>this._nodes.get(s)); ... }
```

`this._nodes` — `Map`, ключ которого **сам element-объект** (см. также `_debugCollectHandles`: `this._nodes.get(i)`). Для нового литерала lookup даёт `undefined`, `_getHandlesToRefresh` возвращает пустой массив, `_refresh` завершается `Promise.resolve(undefined)` — **в UI не уходит ни одного `$refresh`**. Воспроизведено эмпирически (throwaway, не закоммичен): для `getChildren()`-объектов, положенных в `Map`, `map.get({kind:'group',id:'tasks'})` → `undefined`; повторный `getChildren()[0] === первый` → `false`.

Полная инвалидация (`invalidate()` без аргумента → `fire(undefined)`) работает — она попадает в ветку `e.some(o=>!o)` → `$refresh(viewId)`. Поэтому кнопка `Explorer: обновить` и смена фильтров (`setFilterState` → `invalidate()`) визуально работают, и именно это прошли integration-тесты («не бросает»).

**Сценарий:** агент (ADR-004) или `sed` правит `planning/tasks/STEP-006.md` мимо редактора → `FileSystemWatcher` срабатывает → `invalidate('tasks')` → внутренний кэш провайдера очищается, но VSCode об изменении не уведомляется и продолжает показывать закэшированные узлы со старым статусом и старой иконкой. То же после `Mark as done`, `Flag as blocker` и `Delete` — узел остаётся в дереве с прежними данными (удалённый STEP продолжает отображаться).

**Impact:** Scope-пункт «`refresh.ts` — обновление по file watcher на релевантные пути из манифеста» и Implementation plan п.9/п.10 («точечная инвалидация группы вместо всего дерева, чтобы не схлопывать раскрытые узлы») не выполняются фактически, хотя код написан. Это же делает недоказанным пункт 6 Verification sequence («правка STEP-файла извне обновляет дерево без перезапуска»), который не был выполнен (см. раздел «Оценка отклонения»). Ни один тест этого не покрывает: `treeProvider.ts` не имеет unit-тестов вообще, а integration-тест проверяет только факт регистрации команд и отсутствие исключения.

**Fix direction:** хранить стабильные инстансы group-узлов в провайдере (мемоизированный массив, создаваемый один раз в конструкторе) и возвращать/фаерить именно их; альтернативно — временно фаерить `undefined` (полная инвалидация), приняв схлопывание раскрытых узлов. Регрессионный тест: unit-проверка идентичности (`provider.getChildren()` дважды даёт те же ссылки, и объект, передаваемый в `fire`, содержится в них), либо integration-тест на реальном `TreeView` с внешней правкой файла.

**Сценарий:** репозиторий с Harness-слоем и уже существующими `planning/tasks/STEP-*.md`, но `project.initialized: false` — это поддерживаемое состояние (legacy adoption, `docs/harness/UPDATES.md`; `AGENTS.md` §4 явно описывает pre-init режим). **Impact:** в кодовой базе снова возникает асимметрия «один и тот же protocol invariant защищён в command layer и открыт в UI layer» — ровно тот класс дефекта, который закрывал `FIX STEP-005 (F-001)`. Формально это же нарушает `Mutation policy → Forbidden` («переиспользовать pre-dispatch валидацию из STEP-005»), поскольку вместо переиспользования проверка просто отсутствует.

Побочно: `createFollowUpStep` защищён — он делегирует в `harness.addStep`, у которого guard есть. Незащищены именно три прямых writer-действия.

**Fix direction:** вызывать `checkInitGuard(manifest, 'require-initialized')` первым шагом в `markDone`/`flagBlocker`/`deleteArtifact` (с существующим ключом `harness.error.notInitialized`) и дополнительно не показывать mutating-пункты меню при неинициализированном проекте (context key). Unit-тест на guard + integration-тест на fixture-workspace с `initialized: false`.

### F-003 [Blocking] — `canMarkDone` проверяется по закэшированным данным узла, а не по фактическому содержимому файла

**Location:** `src/explorer/actions.ts:56-75` (`resolveTargetStep`), `:186-201` (`markDone`); то же в `flagBlocker` (`:212`).

```ts
const fromNode = typeof arg === 'object' ? findStepNode(arg) : undefined;
if (fromNode) return fromNode;            // ← StepData из дерева, без перечитывания файла
```

При вызове из context-menu VSCode передаёт сам element-узел, поэтому `markDone` выполняет `canMarkDone(step)` над `StepData`, разобранным в момент последней загрузки группы. `writeStepFile` перечитывает файл, но только для записи; `setStatus` верифицирует лишь то, что изменился ровно `status` — verdict он не перепроверяет.

**Сценарий:** дерево загрузило STEP с `Latest verdict: PASS` и непустым Evidence. Затем прошёл `FIX` → повторный `REVIEW` с `FAIL` (или Evidence очищен), файл на диске изменён. Из-за F-001 узел в дереве остаётся старым в принципе неограниченно долго. Пользователь правой кнопкой → `Mark as done` → guard видит устаревший `PASS` → в файл, где стоит `Latest verdict: FAIL`, записывается `**Статус:** Выполнено`.

**Impact:** обходится главный deterministic gate этого STEP (`AGENTS.md` §8/§11, `EXECUTION_PROTOCOL.md` §3: «Статус `Выполнено` нельзя выводить только из текста агента», разрешён только при обязательном review PASS). Сам Implementation plan называет этот сценарий «самый опасный сценарий этого STEP» — guard написан, но применяется к потенциально устаревшему входу, то есть fail-open. Тот же дефект в `flagBlocker` (терминальный статус мог измениться) менее критичен, но однороден.

**Fix direction:** в `markDone`/`flagBlocker`/`deleteArtifact` использовать данные узла только как источник `id`, а `StepData` для guard'а всегда получать свежим чтением файла непосредственно перед записью (уже есть `listAllSteps`/`parseStepFile`); идеально — выполнять guard над тем же контентом, который затем передаётся в `stepWriter`, в одной read-verify-write последовательности. Тест: «в узле PASS, на диске FAIL → запись не происходит».

### F-004 [Non-blocking, Medium] — `canDelete` не учитывает входящие ссылки ADR, хотя план требовал «traceability REQ/ADR»

**Location:** `src/explorer/guards.ts:50-61`; вызывающий код `src/explorer/actions.ts:242-246` читает только STEP и REQ.

Implementation plan п.7: «удаление запрещено, если на артефакт есть входящие ссылки (`Depends on` других STEP, traceability **REQ/ADR**)». Реализация проверяет `allSteps[].dependsOn` и `allReqs[].traceability.step`; ADR не читаются вовсе. При этом `AdrTraceability.step` существует (`src/parser/types.ts:165-168`), `parseAdrFile` уже используется в `model.ts`, `deriveAdrDir` уже есть в `paths.ts`, и реальные ADR это поле заполняют — например `docs/adr/ADR-002-step-file-format.md:52` → `- STEP: STEP-003, STEP-007`.

**Сценарий:** STEP типа `ADR` или `RESEARCH`, на который ссылается только `## Traceability` соответствующего ADR (в `SPEC.md` у связанного REQ стоит `STEP: не запланирован`, и никакой другой STEP на него не зависит). `canDelete` вернёт `{ok: true}`, файл уйдёт в корзину, а в Accepted ADR останется dangling-ссылка — ровно тот класс, который закрывал `FIX STEP-005 (F-001)` и который §1 протокола («ID стабилен и не переиспользуется») запрещает. На текущем состоянии репозитория сценарий не срабатывает случайно (все существующие STEP покрыты REQ-traceability или `Depends on`), поэтому дефект не виден без целевой проверки.

**Fix direction:** дополнить `canDelete` списком ADR (`allAdrs: AdrData[]`) и проверкой `traceability.step`; в `deleteArtifact` подгружать ADR тем же способом, что и REQ. Тест на вход «ссылается только ADR».

### F-005 [Non-blocking, Medium] — `flagBlocker` выполняет две несогласованные записи; при отсутствии секции STEP остаётся `Заблокировано` без причины

**Location:** `src/explorer/actions.ts:222-224`.

```ts
const ok1 = await writeStepFile(stepPath, (c) => setStatus(c, 'Заблокировано'), i18n);
if (ok1) await writeStepFile(stepPath, (c) => setBlocker(c, reason), i18n);
```

Статус записывается и сохраняется **до** попытки записать причину. Секция `## Blocker / Failure reason` по `EXECUTION_PROTOCOL.md` §4 указана как «при необходимости», то есть необязательна; на файле без неё `setBlocker` вернёт `section-not-found`, пользователь увидит только `harness.explorer.error.writeFailed`, а файл останется в состоянии `Заблокировано` с пустой причиной. Это противоречит и §3 протокола («существует конкретный blocker»), и заявленному в Implementation plan п.6 fail-closed контракту — он соблюдён для одной операции, но не для их композиции.

**Fix direction:** применять обе трансформации к одному прочитанному контенту (`setStatus` → `setBlocker` над её результатом) и делать единственную запись; при ошибке любой из них не писать ничего.

### F-008 [Non-blocking, Low] — терминальные статусы захардкожены в трёх местах и не покрыты drift-тестом

**Location:** `src/commands/preDispatch.ts:51` (не экспортируется), `src/explorer/guards.ts:11`, `src/explorer/treeItem.ts:48` (третья, инлайновая копия).

Появление или переименование терминального статуса разойдётся между `contextValue` в дереве, guard'ом `canFlagBlocker` и pre-dispatch STEP-005 молча.

**Fix direction:** вынести набор терминальных статусов в одно экспортируемое место (например, рядом с `preDispatch.ts`, который им уже владеет) и покрыть тестом того же вида, что `statusIcon.test.ts`.

### F-009 [Non-blocking, Low] — production-реализация `ArtifactReader` подчиняется пользовательским exclude-настройкам, в отличие от тестовой

**Location:** `src/explorer/vscodeReader.ts:14-15`.

```ts
const uris = await vscode.workspace.findFiles(pattern);   // exclude === undefined
```

При `exclude === undefined` `findFiles` применяет пользовательские `files.exclude` и `search.exclude`; чтобы их отключить, нужно передать `null`. В workspace, где, например, `planning/**` или `docs/**` попали в `search.exclude`, соответствующие группы дерева окажутся пустыми при физически существующих файлах. `createFsArtifactReader` (по которому идут все unit- и перф-тесты) такого поведения не имеет, то есть две реализации одного порта имеют расходящийся контракт, и ни один тест этого не покрывает.

**Fix direction:** `vscode.workspace.findFiles(pattern, null)`.

### F-010 [Non-blocking, Low] — `Mark as done` из UI создаёт гарантированное расхождение projection-файлов

**Location:** `src/explorer/actions.ts:200-202`.

Запись `**Статус:** Выполнено` в canonical STEP-файл не сопровождается синхронизацией `planning/PLAN.md`, `planning/STATUS.md` и статуса связанного REQ, хотя `AGENTS.md` §10 и `EXECUTION_PROTOCOL.md` §25 требуют, чтобы projection-файлы не расходились с canonical. Ни `## Scope`, ни `## Out of scope` этот вопрос не оговаривают, то есть это не осознанно вынесенное ограничение, а пробел.

**Fix direction:** зафиксировать решение явно — либо предупреждать пользователя и рекомендовать `RECONCILE PROJECT` после действия, либо вынести синхронизацию проекций в отдельный STEP и записать это в `## Out of scope` STEP-006.

### F-011 [Non-blocking, Low] — user-facing строка мимо i18n

### F-012 [Non-blocking, Low] — при отсутствии открытого workspace `viewsWelcome` не показывается

**Location:** `src/explorer/activation.ts:48-49` (ранний `return` до `setContext`) в связке с `package.json → contributes.viewsWelcome[0].when: "harness.isHarnessProject == false"`.
