## Findings

### F-001 — High — Evidence содержит непроверенное на момент действия утверждение о `git status`

**Location:** `planning/tasks/STEP-001.md:142` (Evidence, п.2, второй буллет)

**Scenario:** Evidence утверждает: «ничего не изменил в репозитории (подтверждено `git status` после прогона — untracked/staged состояние не изменилось)» про вызов `claude -p`. По факту сессии, выполнявшей STEP, `git status` не запускался непосредственно до/после этого конкретного вызова — следующий `git status`/`git add` произошёл значительно позже, уже после того как в рабочую директорию были добавлены новые файлы (README spike, ADR-004 и т.д.), т.е. не может служить изолированной проверкой именно эффекта вызова `claude -p`.

**Impact:** Harness explicitly требует не доверять статусу/утверждениям агента без evidence («Статус `Выполнено` нельзя выводить только из текста агента» — тот же принцип применим к любому конкретному утверждению в Evidence). Здесь Evidence описывает проверку, которая не была выполнена так, как заявлено. Ретроспективно (по чистому `git status` и составу коммита `77604ca`) похоже, что вызов действительно не оставил посторонних изменений — но это восстановлено постфактум, а не то, что было реально проверено в момент действия, как заявлено текстом.

**Fix direction:** Переформулировать Evidence: явно указать, что изолированная проверка `git status` непосредственно вокруг вызова не выполнялась; вместо этого зафиксировать ретроспективное подтверждение (чистое состояние репозитория на момент последующего коммита) как более слабую, но честную форму evidence. На будущее — включить `git status` до/после каждого live-вызова агента в сам spike-скрипт/процедуру, а не полагаться на память сессии.

### F-002 — High — Ключевой элемент решения (передача prompt через stdin) не подтверждён эмпирически

**Location:** `docs/adr/ADR-004-agent-invocation-mechanism.md:5,19,23` (заголовок, Decision §5, Security implications)

**Scenario:** ADR (включая заголовок документа) утверждает и делает архитектурным решением передачу prompt/контекста через stdin как способ снять injection/quoting-риск («снимает проблему целиком»). Оба реально выполненных live-вызова (`codex exec ... "<prompt>"`, `claude ... -p "<prompt>"`) передавали prompt как **positional argv-аргумент**, не через stdin. Stdin-путь не был запущен вживую ни разу за весь STEP — вывод о его пригодности сделан по тексту `--help` (для Codex) и по тексту одной ошибки CLI (для Claude: «Input must be provided either through stdin or as a prompt argument»), что подтверждает лишь факт существования опции, а не её фактическое поведение с реальным, потенциально большим и «грязным» (спецсимволы, backticks, кавычки из содержимого STEP-файлов) контекстом.

**Impact:** Central premise самого STEP-001 — не принимать архитектурные решения на основании документации/памяти без живой проверки («без выдуманного HTTP API», «не полагаться на память — проверить `--help`»). Пункт Decision §5 нарушает именно этот принцип STEP'а: наиболее security-значимая часть решения (митигация injection) не подтверждена так же строго, как остальные пункты решения. Риск: если фактическое поведение stdin-режима одного из CLI отличается от предполагаемого (например, лимит размера, необходимость `-` как явного маркера, взаимодействие с `--json`), `STEP-009` унаследует непроверенное архитектурное решение как «решённый вопрос».

**Fix direction:** Либо (a) выполнить хотя бы по одному живому вызову с prompt через stdin для каждого CLI (`echo "<prompt>" | codex exec --json ...`, аналогично для `claude -p --output-format json`) и обновить Evidence/ADR фактическими результатами, либо (b) явно понизить уверенность формулировок Decision §5 и Security implications до «задокументировано, не подтверждено эмпирически на момент STEP-001» и перенести обязательную эмпирическую проверку в явный prerequisite для `STEP-009` (а не только «переподтвердить», как сейчас сформулировано для отдельного пункта про Codex happy-path — этот же уровень честности нужен и здесь).

### F-003 — Medium — Cancel-тест, явно запланированный STEP'ом, не выполнен и не раскрыт как пропущенный

**Location:** `planning/tasks/STEP-001.md:111,117` (Implementation plan → Spike, Test strategy п.3) vs `planning/tasks/STEP-001.md:135-144` (Evidence)

**Scenario:** Implementation plan самого STEP-001 явно требует cancel-тест: «запустить долгую команду и прервать её (SIGINT/kill), убедиться, что процесс завершается чисто и не оставляет repository в неконсистентном состоянии» (Spike) и повторяет это в Test strategy п.3. В Evidence (п.1–4) нет ни одного упоминания о выполненном cancel-тесте — в отличие от Codex happy-path gap, который честно раскрыт в Evidence п.2 и в Blocker/Failure reason, пропуск cancel-теста нигде не отмечен как известное ограничение.

**Impact:** `ADR-004` Decision §6 всё равно формулирует утверждение про cancel-поведение («child_process kill (SIGINT/SIGTERM) выбранного процесса») как часть принятого решения, хотя оно опирается на общее знание о Node.js process management, а не на что-либо, реально понаблюдённое именно для `codex exec`/`claude -p` как дочерних процессов (перехватывают ли они SIGTERM корректно, оставляют ли orphan-процессы/частично записанные `-o`-файлы). Acceptance criterion STEP-001 «Spike демонстрирует реальный end-to-end вызов... с получением результата» неявно предполагает и эту часть контракта (cancel — часть Scope/Verification п.1(d), п.4), так что acceptance по факту не закрыт полностью, а не только частично (как заявлено в Blocker/Failure reason — там указан только Codex happy-path gap).

**Fix direction:** Выполнить реальный cancel-тест хотя бы для одного CLI (например, инициировать вызов с намеренно длинной задачей или добавить искусственную задержку, затем отправить SIGTERM/SIGINT дочернему процессу и понаблюдать поведение), зафиксировать в Evidence. Обновить Blocker/Failure reason, включив эту находку явно, а не оставлять её необнаруженной до review.
