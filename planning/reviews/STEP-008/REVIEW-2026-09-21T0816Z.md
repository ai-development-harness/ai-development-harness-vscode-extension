## Findings

### F-001 — Medium — warning count и manifest-resolved filtering не имеют regression evidence

**Location:** `tests/integration/editor.test.js:22-54`,
`tests/unit/ui/statusBar.test.ts`

Status Bar integration проверяет только наличие текста `Warnings`, exact Problems
command и отсутствие arguments. Он не создаёт/изменяет diagnostics и не
подтверждает, что:

- `onDidChangeDiagnostics` инициирует batched refresh;
- Error/Warning внутри manifest-resolved `taskDirectory` меняет count;
- diagnostics вне `taskDirectory` не попадают в count;
- Information/Hint не попадают в count;
- custom `protocol.taskDirectory` и `sources.status` используются watcher,
  filtering и completion action вместо default layout.

Существующий editor integration позднее действительно публикует diagnostic для
STEP, но Status Bar state до/после этого не сравнивается. Unit suite также не
создаёт `HarnessStatusBar` и не проверяет derived warning state.

**Impact:** REQ-004 требует корректное количество health-warnings, а STEP scope
явно связывает его с diagnostics STEP-007. Ошибка фильтра, listener wiring или
возврат к default paths не уронит текущие tests; один из четырёх основных
индикаторов и manifest-first architecture boundary остаются недоказанными.

**Fix direction:** добавить focused controller/Extension Host regression,
который публикует owned Error/Warning для canonical/custom task directory,
добавляет control diagnostic вне неё и Information/Hint, ждёт bounded polling
изменившегося count, затем очищает diagnostics и дожидается исходного состояния.
Для custom manifest fixture также проверить watcher refresh и exact
manifest-resolved `sources.status` URI.

## Verdict rationale

Production implementation визуально использует `manifest.protocol.taskDirectory`
и `onDidChangeDiagnostics`, но acceptance нельзя считать доказанным только
inspection. Warning count является прямым продуктовым контрактом REQ-004, а не
второстепенной веткой. Supplemental verdict: FAIL. Требуется `STEP FIX STEP-008`
и новый независимый review.
