## Findings

### F-001 — Medium — Regression не доказывает инвалидацию отображаемого CodeLens и пропускает fire после неуспешного refresh

**Location:** `tests/integration/editor.test.js:146-170`;
`src/editor/activation.ts:42-52,85-89`.

**Scenario:** Given STEP открыт в редакторе и VSCode уже закэшировал его
CodeLens, when внешний процесс создаёт или удаляет ADR, then требуемый путь —
`FileSystemWatcher` → успешная замена index → `onDidChangeCodeLenses` →
перерисовка уже показанных lenses. Новый integration-тест после каждого
изменения сам повторно вызывает `vscode.executeCodeLensProvider`. Эта команда
заново запрашивает provider и читает уже обновлённую переменную `index`, поэтому
тест останется зелёным даже при полном удалении `onDidChangeCodeLenses` и
`codeLensChanges.fire()`: defect предыдущего review он не воспроизводит.

Вторая ветка того же lifecycle также не защищена: если `loadIndex` отклонится,
`refreshIndex` возвращает прежние `{ manifest, index }`; caller считает это
успешным `next`, повторно присваивает старый index и вызывает
`codeLensChanges.fire()`. То есть событие сейчас не ограничено успешной
заменой index, хотя Evidence STEP утверждает обратное.

**Impact:** production wiring для обычного create/delete выглядит корректно,
но exact regression, из-за которого предыдущий review завершился FAIL, не
зафиксирован тестом. Удаление либо поломка event wiring не будет обнаружена
suite, а failure refresh публикует ложную инвалидацию поверх stale index. Это
оставляет основной внешний Harness-flow без доказательства актуальности уже
видимого CodeLens и делает recorded Evidence сильнее фактической проверки.

**Fix direction:** Выделить минимальный тестируемый refresh/event seam. Unit
regression должен подписаться на `onDidChangeCodeLenses` и доказать: после
успешной замены index приходит ровно один `fire`, после failed refresh событие
не приходит, после dispose watcher/timer больше не публикуют события. Если
VSCode API позволяет наблюдать presentation cache в Extension Host, дополнить
этим текущий create/delete case; повторный `executeCodeLensProvider` можно
оставить как проверку содержимого нового index, но не считать доказательством
event invalidation.
