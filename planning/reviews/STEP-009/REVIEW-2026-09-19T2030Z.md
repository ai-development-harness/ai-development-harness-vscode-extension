## Findings

### F-001 — Medium (verification/security regression) — valid path не проверяет дополнительную error notification

**Location:** `tests/integration/commands.test.js:148-197`, особенно
`175-185`; ADR-011 Decision 3; `planning/tasks/STEP-009.md:46-49,57-58,96-99`.

Extension Host test глобально перехватывает `showErrorMessage` в
`errorMessages`, но для valid `STEP ADD` / `PROJECT QUICK FIX` snapshot делает
только для Output Channel и `warningMessages`. Поэтому suite доказывает exact
значение двух ожидаемых вызовов, но не доказывает отсутствие третьего UI sink.

Конкретная regression остаётся зелёной: Command Palette path может дополнительно
вызвать `showErrorMessage` с raw pure-normal intent, hostile text или exact
text-command, а затем сохранить текущие exact Output Channel и warning calls.
Все assertions строк 182-185 и no-spawn checks пройдут, хотя original intent
попадёт в notification вопреки ADR-011. Наличие отдельного pure-normal fixture
не ловит эту ветку, потому что `errorMessages` в valid scenario не читается.

**Impact:** текущая production implementation не создаёт такую notification и
выглядит безопасной, однако durable Extension Host evidence всё ещё не
доказывает never-echo для всей notification surface. Будущая диагностическая
ветка в `handleCommand()` или `dispatchViaAgent()` сможет раскрыть user intent
при полностью зелёных обязательных regressions, что нарушит REQ-005/ADR-011.

**Fix direction:** в каждом valid text scenario сохранить `errorStart` и
потребовать `errorMessages.slice(errorStart)` равным `[]`. Если valid path
когда-либо намеренно получит error notification, проверять её exact safe
localized value и применять к ней те же negative assertions для sentinel,
secret/control bytes и original command.
