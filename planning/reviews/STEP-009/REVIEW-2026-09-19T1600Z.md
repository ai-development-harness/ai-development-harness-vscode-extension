## Findings

### F-001 — High (security) — Windows cancel запускает `taskkill` через недоверенный executable search

**Location:** `src/api/executors.ts:71-74`.

На Windows `terminateProcessTree()` дважды вызывает
`execFile('taskkill', ...)` без абсолютного trusted path. Если CWD Extension
Host или `PATH` содержит каталог, контролируемый открытым workspace (например,
VS Code запущен из checkout с таким PATH), Windows executable search может
выбрать подложный `taskkill.exe` раньше системного.

**Scenario:** repository размещает `taskkill.exe` в доступном search-order
каталоге. Пользователь отменяет agent invocation через Ctrl+C либо extension
вызывает `dispose()`. Вместо системной утилиты запускается repository-controlled
process с правами VS Code пользователя.

**Impact:** произвольное выполнение кода на security-sensitive cancel boundary;
это обходит уже введённое требование trusted absolute executable для
Codex/Claude/Git.

**Fix direction:** использовать проверенный абсолютный
`%SystemRoot%\System32\taskkill.exe` либо Windows Job Object/process-tree API,
не выполняющий PATH/CWD lookup. Добавить Windows-focused regression с fake
`taskkill.exe` в CWD/PATH и доказать, что он не запускается.

### F-002 — High (correctness) — result отвергает валидные canonical next commands вне девяти agent-команд

**Location:** `src/api/executors.ts:34-42`;
`src/api/contextBuilder.ts:69`; REQ-005.

Prompt требует `nextCommand: "CANONICAL COMMAND or null"`, но private
`isCanonicalCommand()` принимает только девять mutating MVP-команд. Валидные
по repository CTS команды `GIT CHECK`, `PROJECT STATUS`, `STEP NEXT`, а также
разрешённые chain forms отвергаются как malformed.

**Scenario:** успешный `STEP RUN STEP-009` изменяет workspace и возвращает
`{"summary":"готово","changedFiles":[...],"nextCommand":"GIT CHECK"}`.
`structuredResult()` классифицирует весь terminal result как malformed.
Dispatcher не выполняет reload, не показывает summary и не предлагает
следующую команду, хотя mutation уже произошла.

**Impact:** нарушены result/reload/next-command части REQ-005 на обычном
post-STEP пути; ADR-003 сознательно оставляет Git вне UI MVP, но не делает
`GIT CHECK` неканонической командой и не запрещает показать её пользователю.

**Fix direction:** валидировать `nextCommand` через единый CTS command contract,
а не локальную урезанную regex; поддержать всю canonical command surface и
допустимые chain forms либо явно задокументировать более узкую result schema.
Добавить positive regressions минимум для `GIT CHECK`, `PROJECT STATUS` и
`STEP NEXT`, сохранив negative case для действительно невалидного текста.

### F-003 — Medium (verification) — progress и cancel safety не доказаны через реальные transport/process seams

**Location:** `tests/unit/api/agentDispatcher.test.ts:81-90`;
`tests/unit/api/executors.test.ts:54-63,133-150`;
`tests/integration/commands.test.js:66-112`.

Dispatcher test вручную вызывает progress callback из fake executor, а executor
test с реальным JSONL process не передаёт и не проверяет callback. Extension
Host happy path не наблюдает Output Channel, progress, summary или next-command
UI. Cancel tests проверяют только resolved `cancelled`: fake process не создаёт
descendant с delayed marker/write, поэтому отсутствие живого потомка и
изменения файла после Ctrl+C не проверяется.

**Scenario:** реальный Codex transport перестаёт передавать `item.progress` в
Output Channel либо process group оставляет descendant, который пишет файл уже
после возврата cancelled. Все текущие gates остаются зелёными.

**Impact:** прежние F-004/F-006 и acceptance «progress/result»/«Ctrl+C без
порчи состояния файлов» имеют false-positive verification.

**Fix direction:** добавить executor regression с реальным fake JSONL progress
и captured callback; на dispatcher/Extension Host seam проверить порядок
`[progress]` до `[result]` и user-visible next command. Для cancel запустить
descendant с delayed marker/write, отменить invocation и доказать отсутствие
потомка, marker/file mutation, partial result и reload.

### F-004 — Medium (verification) — заявленный Windows regression context boundary отсутствует

**Location:** `tests/unit/api/contextBuilder.test.ts:27-38`;
`planning/tasks/STEP-009.md:323-326`.

Fix evidence заявляет устранение separator-dependent F-005, но единственный
test выполняется на текущем POSIX fixture path. Нет mocked Windows resolved
path либо Windows CI assertion, которое доказывает inclusion связанного REQ и
исключение полного SPEC/соседнего REQ при `\\` separators.

**Impact:** корректное code change есть, но cross-platform regression из
предыдущего fix direction не закреплён и может вернуться при следующем
рефакторинге resolver/context builder.

**Fix direction:** добавить platform-independent seam для resolved paths или
целевой Windows CI test; явно проверить, что в prompt есть связанный REQ и нет
соседнего при Windows separators.
