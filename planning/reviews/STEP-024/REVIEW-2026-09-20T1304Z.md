## Findings

### F-001 — Medium — Заявленная в Acceptance criteria и Implementation plan отрицательная regression на отсутствие `.project/**` fallback не реализована

**Location:** `tests/**` (ни одного нового test case во всём diff);
`planning/tasks/STEP-024.md:63` (acceptance criterion),
`planning/tasks/STEP-024.md:113-121` (Implementation plan, шаг 4),
`planning/tasks/STEP-024.md:79` (Deliverables — «Focused regression tests»).

**Scenario:** Given acceptance criterion «Unit и Extension Host regressions
доказывают работу на fixture с `.harness/**` **и отсутствие fallback к
`.project/**`**» и plan шаг 4, явно требующий «отрицательную проверку, что
наличие либо отсутствие `.project/manifest.yaml` не образует fallback»;
When просмотрен весь diff `tests/**` — он состоит **исключительно** из
подстановок путей в существующих тестах и переноса fixtures, ни одного нового
`it(...)`/`test(...)` не добавлено;
Then вторая половина acceptance criterion не доказана ни одним deterministic
gate. Текущее отсутствие fallback установлено только статически (grep/код-ревью),
что по AGENTS.md §8 не является заменой реальной проверке.

Усугубляет: `tests/unit/explorer/paths.test.ts:25` сравнивает `relPath` с самой
константой `MANIFEST_REL_PATH` — тавтология, не фиксирующая литерал
`.harness/manifest.yaml`. Ни один тест в репозитории не пинит это значение
(`grep -rn "'\.harness/manifest\.yaml'" tests/` → только пути к fixtures).

**Impact:** Regression-protection, а не текущая корректность: функционально всё
верно и эмпирически подтверждено. Но ключевой Forbidden-пункт STEP-024
(«Fallback, probing или dual-layout поддержка `.project/**`») не защищён ни одним
failing-тестом. Будущая «обратная совместимость» в `resolveConfigPath` или в
любом из 5 consumer-модулей пройдёт весь зелёный suite. Кроме того, при
возврате константы к `.project/manifest.yaml` unit-suite (322 теста) останется
зелёным целиком — поймают только Extension Host suites, и только по побочному
эффекту отсутствия `.project/` в fixture-workspace.

**Fix direction:** Отдельным `STEP FIX STEP-024` добавить focused unit-тесты
(дёшево, без production-изменений):
1. пин литерала — `expect(HARNESS_MANIFEST_REL_PATH).toBe('.harness/manifest.yaml')`
   и `expect(MANIFEST_REL_PATH).toBe('.harness/manifest.yaml')`;
2. негативная проверка на tmp-директории, содержащей **только**
   `.project/manifest.yaml`: `parseManifest(join(dir, HARNESS_MANIFEST_REL_PATH))`
   возвращает типизированный `err` kind `not-found`, а не читает legacy-файл;
3. проверка, что `watchedPaths(manifest)` / `stepEditorWatchPatterns(manifest)`
   не содержат ни одной строки с префиксом `.project/`.

## Verdict rationale

Реализация функционально корректна и полна: `.project/**` отсутствует в `src/**`
и в собранном bundle, все bootstrap paths идут через единственный
extension-owned locator, CTS bundled и идентичен прежнему контракту, все восемь
команд Verification воспроизведены ревьюером с exit 0, плюс независимо
выполнена не заявленная CI-gated pre-activation suite. Doc sync выполнен без
нарушения immutability.

Однако третий acceptance criterion выполнен наполовину: «работа на fixture с
`.harness/**`» доказана, «отсутствие fallback к `.project/**`» — нет, потому что
явно запланированная отрицательная regression (plan шаг 4) не реализована и не
раскрыта как сознательно пропущенная, а Deliverable «Focused regression tests»
не поставлен ни одним новым тестом (F-001). Дополнительно Evidence содержит
численно неверное утверждение о drift (F-002) и не фиксирует единственный gate,
покрывающий изменённый CI-тест (F-003). По AGENTS.md §8 и §11 перевод STEP в
`Выполнено` при недоказанном acceptance criterion недопустим.

Verdict `FAIL`. Объём доработки узкий и не затрагивает production code:
`STEP FIX STEP-024` — добавить focused тесты из F-001, поправить Evidence по
F-002/F-003. F-004 — кандидат в `PROJECT QUICK FIX`.
